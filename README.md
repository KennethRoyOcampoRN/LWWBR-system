# Lucky Waku-Waku Resort Command Center

See `spec.md` at the repo root for the full product/technical spec. This
README tracks what actually works, milestone by milestone, and is updated
at the end of each one per spec §12 rule 11.

## M0 — Scaffold

### What works

- npm workspaces monorepo: `apps/api` (Express + TypeScript), `apps/web`
  (Vite + React 19 + Tailwind), `packages/shared`.
- Full Prisma schema for every model in spec §6 (including the Phase 2
  tables, modeled now per spec §11's backlog note). `prisma generate`
  succeeds.
- `RealtimeAdapter` and `StorageAdapter` interfaces (`apps/api/src/adapters/`)
  with Supabase-only implementations, matching spec §3.1 — no Socket.IO or
  local-disk implementation exists, by design.
- `GET /api/v1/health` — returns adapter resolution and region, no network
  or DB calls.
- `apps/web` fetches `/api/v1/health` on load and renders it (scaffold
  only; the real Command Center is M2+).
- `vercel.json` and `supabase/config.toml` are written to spec but **not
  deployed and not run** — see "Unverified" below.
- ESLint (flat config, Node/browser globals split correctly) and Prettier
  are wired and clean across the whole repo.
- `npm run typecheck`, `npm run lint`, `npm run build`, and `npm test` all
  pass. `npm run dev` boots both apps together and the web dev server
  proxies `/api` through to the API on port 3001.
- `scripts/check-serverless-safety.sh` greps `apps/api/src` for
  `setInterval` (hard fail) and `setTimeout` (flagged for manual review) —
  currently clean.

### How to run it

```bash
npm install
cp apps/api/.env.example apps/api/.env   # then fill in from `supabase start` output
supabase start                            # see "Unverified" below
npm run dev                               # api on :3001, web on :5173
```

### Unverified — pending a local `supabase start` run

**This environment has Docker's CLI but no running daemon, and the
Supabase CLI isn't installed.** `supabase start` could not be run here, so
two pieces of spec §11 M0's acceptance criteria have never actually been
executed against a real Supabase instance:

1. **Storage round-trip** (`apps/api/test/adapters/storage.roundtrip.test.ts`)
   — upload, download, and signed-URL generation through
   `SupabaseStorageAdapter` against local Supabase Storage.
2. **Realtime round-trip** (`apps/api/test/adapters/realtime.roundtrip.test.ts`)
   — a broadcast emitted through `SupabaseRealtimeAdapter` received by a
   subscribed client, against local Supabase Realtime.

Both tests exist, compile, and are wired to skip cleanly
(`describe.skipIf`) when `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY`
aren't set — confirmed in this session. What's **not** confirmed is that
they pass against a real local stack. A manual run with placeholder
credentials confirmed the adapters make real network calls and fail
correctly when nothing is listening (no mocking, no fake success) — see
git history for that run — but that is not the same as a green pass
against a live instance.

`supabase/config.toml` is hand-authored (not generated by `supabase init`)
and has never been read by a real Supabase CLI. It may need adjusting —
see the comments in the file itself.

**Action needed:** run `supabase start` locally (Docker required), copy

```bash

```

Report back whatever breaks. This is carried forward as the top debt item

### Known gaps carried into M1 (not blockers, just not built yet)

- `Booking.status`, `Notification.type`, `Incident.severity`, and
  `Expense.status` are `String` in the Prisma schema, not enums — spec.md
  didn't enumerate their values. `Booking.status` needs a real state
  machine before M4; the others are Phase 2.
- This sandbox runs Node 22, not the Node 24 the spec pins (`.nvmrc`,
  `package.json#engines`). `npm install` warns (`EBADENGINE`) but every
  command still ran correctly. Confirm on Node 24 before relying on this.
